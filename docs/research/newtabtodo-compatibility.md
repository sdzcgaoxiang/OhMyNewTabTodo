## 原版数据访问行为

### 浏览器扩展环境

检测到浏览器 storage.sync API 后使用该存储区域，不以是否实际开启账号同步为判断依据。

| 内容 | 存储方式 |
| --- | --- |
| 卡片 | 每张卡片一个 `card-*` 键 |
| 看板 | 每个看板一个 `board-*` 键 |
| 看板顺序 | `boardOrder` 数组 |
| 看板内顺序 | 看板对象中的 `cardIds` 数组 |
| 常用链接 | `app_bookmarks` |
| 设置 | `options`，由单独的读取逻辑处理 |
| 迁移标记 | `isMigrated` |
| 旧版任务数据 | `app_todos` 中的 JSON 字符串 |
| 旧数据迁移备份 | `backup-v<version>` |

读取任务时获取同步存储并按键前缀组装卡片和看板。保存任务时，将当前卡片、看板、顺序和迁移标记合并为一次 set 调用。

注意：setData 本身只设置键，不删除已不存在于传入对象中的旧键。后续执行原始删除处理函数并模拟持久化，已复现看板/卡片删除后存储键仍残留，详见 `newtabtodo-audit.md`。

没有扩展存储 API 时，任务和书签逻辑使用 localStorage 中的 JSON。不能据此认为所有模块都完整支持非扩展环境。

原版有从整段 JSON 转换到独立键的迁移逻辑，并会规范化 card-/board- 前缀。新兼容层必须考虑旧 ID 形式，而不能只接受当前前缀。

## 原版导出文件结构

| 层级 | 字段 |
| --- | --- |
| 顶层 | `id`, `appVersion`, `bookmarks`, `boardOrder`, `boards`, `cards` |
| 看板 | `id`, `title`, `cardIds`, `isHidden`, `createdAt`, `updatedAt` |
| 卡片 | `id`, `title`, `completed`, `description`, `dueDate`, `dueTime`, `labels`, `tags`, `history`, `priority`, `createdAt`, `updatedAt` |
| labels 元素 | `id`, `text`, `type` |
| tags 元素 | `id`, `color`, `text` |
| bookmarks 元素 | 导出直接使用当前书签数据；导入端使用 `id`, `name`, `url` |

许多字段是可选的，导出端根据值是否存在决定是否写入。`boards`、`cards` 是以 ID 为键的对象，不是数组。顶层 `id` 是导出时生成的时间戳，不是任务 ID。

该导出不包含完整应用设置。没有导出的信息无法凭导出文件还原。对更多历史版本的兼容范围需要真实样例或对应版本证据验证。

## 导入行为与隔离验证

方法：在 Node VM 内使用本机安装包的原始导入、导出函数及其运行依赖，模拟浏览器存储，禁用真实统计和下载。样例为人工构造。没有在真实 Chrome 页面执行导入，也没有读写用户待办。

| 场景 | 结果 |
| --- | --- |
| 合法看板、卡片与空书签数组 | 返回成功，写入 1 张卡片 |
| 目标存储缺少 app_bookmarks，输入文件合法 | 在写入前抛出 undefined is not iterable |
| 模拟 storage.sync.set 因配额失败 | 返回成功，卡片实际写入数为 0 |
| 输入中看板标题为空字符串 | 在写入前报 file corrupted |
| 调用原版导出后，再导回有原始卡片的存储 | 导入成功，卡片总数从 1 变为 2 |

阶段结论：存在可复现缺陷，不能认定所有文件都一定失败。随后通过用户文件及 F12 堆栈确认本次直接原因是缺少 bookmarks，见下文。

其他已观察行为：

- 每次导入重建看板、卡片和标签 ID，追加到已有内容。
- 书签按 URL 去重，合并后最多保留 15 项。
- 书签名称、看板标题、卡片标题分别裁剪到 15、35、120 个字符。
- 先写书签，再写任务；没有覆盖两者的事务。
- 存储封装将部分异常转为错误对象，导入调用方没有检查错误对象。
- 类型检查不等于关联完整性检查；看板顺序、对象键、对象 ID、cardIds 的关系需要新兼容层明确校验。

## 建议的兼容验收边界（待讨论）

1. 0.2.0 正常导出文件能直接导入，不要求用户手工改 JSON。
2. 保留顺序、隐藏/完成状态、描述、日期、标签、优先级、历史及链接等已有信息。
3. 导入预检不修改数据；显示数量和异常；失败时不留下半份导入结果。
4. 重复导入的语义明确区分恢复、合并和复制，不暗中制造重复数据。
5. 不静默截断内容；未知字段保留或报告；缺失关联先报告，必要时提供可审查的修复策略。
6. 不把原版导入器的缺陷复制进新实现。兼容旧文件与保证旧程序成功导入是两件事。
7. 建议提供原版格式导出，以及含设置、格式版本等信息的新完整备份格式；是否需要双向兼容仍待用户确认。
8. 旧格式无法表达的新字段，在导出旧格式前明确提示。
9. 导入旧格式时，缺失设置不能导致现有设置被意外重置。
10. 同步、导入与多个已打开页面之间需要统一的写入与刷新规则，防止旧页面写回覆盖导入结果。

## 用户失败文件的验证结果

用户随后提供 reference 目录中的 0.2.0 导出文件。只读结构分析结果：JSON 语法有效，文件大小 2,214 字节，含 3 个看板、7 张卡片，boardOrder 只有 2 个看板，缺少顶层 bookmarks 字段。这里不记录任务内容或实际对象 ID。

使用原版函数和隔离模拟存储得到以下结果，输入变体仅在内存构造，没有修改用户文件或真实浏览器数据：

| 输入 | 结果 |
| --- | --- |
| 原文件，模拟目标书签为空数组 | 写入前抛出 file corrupted，写入次数 0 |
| 仅在内存补 bookmarks 空数组 | 返回成功，写入 7 张卡片，但只有 2 个合法 board-* 键，并出现 undefined 键 |
| 补 bookmarks，并将遗漏看板追加到 boardOrder | 返回成功，写入 3 个看板、7 张卡片，没有 undefined 键 |
| 模拟源存储没有 app_bookmarks，调用原版导出函数 | 导出结果确实缺少 bookmarks 字段 |

直接根因：导出器允许书签值为 undefined，JSON 序列化时省略该字段；导入器却要求 bookmarks 必须为数组，否则报 file corrupted。文件与当前导入器不兼容，不代表用户手工损坏了文件。

用户提供的真实 F12 堆栈为 `Error: file corrupted at index.ba38.js:1:26069`。核对本机同版本文件，该位置正对应 bookmarks 数组校验后的抛错语句（throw 起始列 26063）。真实报错位置、输入文件缺失字段和隔离复现相互吻合，已确认本次失败的直接原因。

第二个缺陷：导入器只为 boardOrder 中的看板创建新 ID，但随后遍历全部 boards；不在顺序表中的看板无法取得新 ID，最终写入 undefined 键。该文件中额外看板引用 4 张卡片。仅让导入返回成功不足以证明关联关系正确。

额外看板为何在用户文件中残留尚未确定；后续已独立复现原版删除后的存储残留，但不足以还原用户操作历史。不能自动把它当成用户希望恢复的看板；追加到 boardOrder 仅用于隔离验证，不是已确认的修复策略。

对新版兼容要求的补充：

- 对原版合法生成但缺少 bookmarks 的文件，按无书签处理并告知用户。
- 将未列入顺序表的看板保留为待确认的恢复内容，避免静默丢弃或自动复活。
- 用户确认恢复前，展示数量、关联关系和恢复选择。
- 导入目标自身缺少书签字段的情形也要兼容，否则即使修好输入仍可能触发另一条异常路径。
- 原始文件包含私人内容，已添加 .gitignore 排除 reference 和 private-backups；尚未初始化 Git。可重复审计脚本使用人工构造样例。
