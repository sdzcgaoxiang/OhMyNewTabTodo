# 数据层方案讨论材料

状态：第一版方案已确定并实现；后半部分保留历史同步调研。

## 当前范围与候选方案（2026-10-27 更新）

用户已明确第一版先做本机使用及导入导出，暂不考虑 Chrome 跨设备自动同步。下方以同步为中心的旧方案比较保留为历史调研，不再作为第一版待选方案。

曾比较的本地方案：

| 方案 | 适用点 | 需要承担的工作 |
| --- | --- | --- |
| chrome.storage.local | 扩展专用键值存储，接口少；默认容量 10 MB，可按需申请 unlimitedStorage | 多键关系、并发写入、完整导入的提交与恢复机制需要自行设计；没有 IndexedDB 那样的多对象存储事务接口 |
| IndexedDB | 浏览器本机数据库，支持事务、结构化对象和索引 | 需要维护数据库结构升级、事务边界、多标签页更新通知；API 封装需保持简单 |

最终选择：按用户“尽可能与参考源码设计一致”的要求，采用 `chrome.storage.local`，保留 `boards/cards/boardOrder` 业务结构。使用单个版本化 `app_state` 记录保存任务、设置、书签和最多 3 份恢复快照，避免原版多键分步写入及删除残留。后台 service worker 是唯一写入者，每次操作串行读取最新状态后保存，成功后才返回；页面订阅变化。编辑检查旧对象基线，导入/恢复/清空检查 revision，冲突时拒绝覆盖。

IndexedDB 不受 chrome.storage.sync 的 100 KB/单项 8 KB 限制，但仍有浏览器及磁盘资源约束，不能描述为无限容量。即使使用事务，也必须采用事务内重新读取与字段更新，避免将旧页面快照整份覆盖回去。

已实现的数据流程：旧文件 → 兼容校验/转换 → 导入预览 → 后台重新校验 → 单次 storage.set 提交完整记录；导出读取一个已保存快照。这里不声称 storage API 提供数据库事务：一致性依赖单写入口和单记录提交，写入失败必须保留原记录并传播错误。

本地保存与外部 JSON 备份是不同的保护层。跨电脑暂通过手动导出/导入完成；跨设备自动同步的算法、队列和服务本期不实现。只保留清晰的数据访问边界，不预先搭建同步框架。

导入提供合并、替换和作为副本模式；5 MiB 文件上限独立于存储配额。恢复快照与正式数据共同占用默认 10 MB 本地配额，可能让小于文件上限的导入仍保存失败；此时拒绝整次操作，不自动丢弃恢复点。第一版不申请 unlimitedStorage。

参考：[Chrome Storage API](https://developer.chrome.com/docs/extensions/reference/api/storage)、[IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API)。

## 已有事实带来的约束

1. 原版把每次页面快照直接写入 Chrome 同步存储；删除残留、写入错误被忽略、旧快照覆盖已复现。
2. 旧文件兼容是输入输出协议要求，不要求内部采用原版键结构。
3. 导入必须先校验，在明确的提交边界内完成；设置、卡片、看板和书签不能各自成功一部分却报告整体成功。
4. 本地保存成功、进入同步队列、同步 API 接受写入、另一设备实际读取到，是不同状态。Chrome API 的 set 完成不能当成对端已收到确认。
5. 新扩展身份与原扩展不同，Chrome 不会自动把原扩展存储交给新扩展。
6. 旧格式没有完整设置；未知字段、额外看板和历史残留不能静默丢弃。

## Chrome 同步存储约束

2026-10-26 核对官方文档：sync 总量 102,400 字节、单项 8,192 字节、最多 512 项；写入操作每分钟最多 120 次、每小时最多 1,800 次。超限会失败。按卡片一个键会同时受条目数与容量约束；增加本地数据库不会消除同步通道这些限制。

官方依据：[Chrome Storage API](https://developer.chrome.com/docs/extensions/reference/api/storage)。浏览器提供 onChanged 事件，但应用仍需处理版本、合并、重试与删除传播。

## 候选方案

| 方案 | 存储和同步 | 优点 | 代价/局限 |
| --- | --- | --- | --- |
| A：同步存储为主 | 继续使用 Chrome sync，统一写入模块；版本化数据；避免旧页面全量覆盖 | 接近原版，无独立服务；初期模块较少 | 仍受小容量限制；跨键导入、备份、并发控制复杂；需要暂存/提交标记而非假设有数据库事务 |
| B：本地数据库为主，Chrome sync 作为传输 | 本地事务数据库持有正式数据和待同步记录；独立同步模块使用 Chrome sync | 本地保存、恢复点、批量导入可更清晰；网络故障不阻断本地编辑 | 必须实现版本、删除标记、冲突、副本和补偿；同步容量仍小；不能靠“加个同步接口”完成 |

自建服务/WebDAV/云盘可作为后续方向，不作为本轮默认第三方案，因为会改变用户配置、权限、运维和隐私成本。

## 历史工程倾向（已不适用于第一版）

如果本项目优先确保可靠导入、离线编辑和后续维护，我倾向 B，但前提是把同步模块作为第一版正式工作量，并明确同步容量超限时的行为。

如果目标是最少模块、完全接受 Chrome sync 的容量边界，A 仍可行；但不能把单点写入、存储监听或延迟写入当作完整冲突解决方案。

目前不选数据库库、构建工具或具体合并算法。先确定同步使用需求和产品承诺，再给出可评审设计。

## 两个方案都必须回答的问题

### 写入与并发

- 同一浏览器多个页面的写入如何协调，后台退出后如何恢复。
- 修改以具体操作/字段补丁还是整对象为单位，如何检测过期 revision。
- 两台设备改同一卡片时如何合并；无法安全合并时如何保留双方版本。
- 排序、跨看板移动和删除与编辑冲突如何处理。
- 墙上时钟可能不准，不能只依赖 updatedAt 比较就宣称解决冲突。

### 删除与重连

- 用显式删除标记传播删除，避免旧设备重连让已删除对象复活。
- 删除标记何时能清理，长期离线设备如何重新建立基线。
- 备份恢复是新变更还是整库替换，如何避免旧副本再次覆盖恢复结果。

### 导入和备份

- 预检、恢复点、正式写入、提交确认以及失败恢复的边界。
- 未列入顺序的看板作为待确认内容保留，不能根据猜测自动恢复。
- 缺失 bookmarks 按旧导出器兼容行为处理，既有书签如何合并由导入模式决定。
- 同一来源重复导入如何识别；恢复、合并、副本模式分别定义 ID 处理。
- 原版格式导出与新版完整备份分开；旧格式无法表示的信息先告知用户。

### 容量与用户反馈

- 写入前估算同步容量，实际失败仍要处理。
- 本地成功但同步失败必须可见，不能给笼统的“全部保存成功”。
- 不静默只同步部分任务；是否允许显式本地保留，以及如何恢复全量同步需要设计。
- 不承诺秒级同步；如果用户需要对端确认，需要额外设计协议。

### 开源维护

- 兼容转换器、业务规则、存储适配和同步模块分开测试。
- 版本化内部模型和公开备份格式；保留历史迁移样例。
- 错误码和不含内容的诊断数据可供用户主动导出。
- 测试必须覆盖旧版本升级和模拟同步冲突，不只覆盖页面正常操作。
